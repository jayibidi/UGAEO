## 三、完整上架流程（从 0 到公开）

### 3.1 本地建仓与首次提交

```bash
cd /c/Users/jayib/Documents/Wechat

git init -b main
git add -A

# 关键校验：这四类文件绝对不能出现在待提交列表里
git status --short | grep -E "node_modules|/dist/|\.zip$|\.workbuddy" # 应该无输出
# 反向校验：被 index.ts 引用的适配器必须在列表里
git status --short | grep xiaohongshu.ts                              # 必须有输出

git commit -m "chore: initial commit"
```

首次提交前请再确认一次 `git log` 是空的 —— 之后所有历史都在这个提交之上，**推上去之后再想删除某个文件就得改写历史**。

### 3.2 在 GitHub 建仓库

两种方式，任选：

**命令行（需要已安装并登录 `gh`）**

```bash
gh auth status
gh repo create jayibidi/UGAEO --public --source=. --remote=origin --push
```

**网页**

1. github.com → New repository
2. Owner 选 `ugaeo`（组织）或你的个人账号，Name 填 `UGAEO`
3. **不要**勾选 "Add a README / .gitignore / license"（本地已有，勾了会冲突）
4. 建完执行：

```bash
git remote add origin https://github.com/jayibidi/UGAEO.git
git push -u origin main
```

### 3.3 仓库设置（推上去之后 5 分钟就能做完）

| 位置 | 填什么 |
|---|---|
| About → Description | `开源免费的跨平台文章同步 Chrome 扩展：公众号一键分发到知乎、掘金、CSDN、头条号等 34 个平台` |
| About → Topics | `chrome-extension` `wechat` `article-sync` `zhihu` `juejin` `csdn` `content-distribution` `mcp` `typescript` |
| About → Website | 你的控制台地址（现在 README 里用的 `https://api.ugooto-ai.com/console`） |
| Settings → Branches | 保护 `main`：禁止直接 push、要求 CI 通过、要求 PR 评审（自己开发可以先只开「要求 CI 通过」） |
| Settings → General | 关掉 Wiki（用 docs/ 目录）、关掉 Projects（暂时用不上） |
| Security | 开启 Dependabot alerts + secret scanning（公开仓库免费） |

### 3.4 打第一个 Release

```bash
pnpm typecheck && pnpm test
pnpm bundle                              # 产出 ugaeo-v2.4.2.zip

git add -A && git commit -m "chore(release): v2.4.2"
git tag -a v2.4.2 -m "v2.4.2"
git push --follow-tags

gh release create v2.4.2 ugaeo-v2.4.2.zip \
  --title "v2.4.2" \
  --notes "修复 InfoQ / 快懂百科 未登录却显示已登录；新增平台自检页；统一版本号"
```

Release 的 zip 是**唯一应该出现在 README 安装区**的下载地址：`https://github.com/jayibidi/UGAEO/releases/latest`。这样每次发版自动更新，不会再出现「README 里挂着 2.0.9 老包」的情况。

## 四、README 该怎么写

现在这份 README 有 368 行，信息很全，但结构是「功能罗列 + SEO 问答」，开源读者最想先看到的三件事（这是什么 / 我凭什么信它 / 怎么装）被压在了后面。建议按下面的骨架重排，**前 300 字必须回答完这三个问题**。

```
1. 一句话定位 + 3 张徽章（release / license / CI）
2. 一张图或一段 15 秒演示（GIF 最好，退而求其次放控制台截图）
3. 它解决什么问题（3 行以内，不要写"提升效率"这种空话）
4. 安装（两个入口：Release 下载 / 源码构建；商店链接等真上架了再放）
5. 工作原理与隐私（这是本项目的核心卖点：无服务器、不模拟登录、只用自己的 Cookie）
6. 支持平台表（**必须与代码一致**，标注"可直发 / 仅草稿 / 无需登录"三态）
7. 快速上手（3 步，配截图）
8. 进阶（AI / MCP / 控制台 / 自检）
9. 开发（pnpm 命令、目录结构、如何新增一个平台 → 链到 docs/adapter-spec.md）
10. 常见问题（只留真实被问到的，别堆关键词）
11. 贡献 / 许可证 / 上游署名
```

几条硬规则：

- **平台表必须可验证**。建议直接在表头注明「以 `BUILT_IN_ADAPTERS` 为准」，并在 CI 里跑一致性测试 —— 你现在已经有 `adapter-consistency.test.ts`，把它接进 CI 就能防止 README 再次漂移。
- **不要用营销语气**。「神器」「必备」「解放生产力」在开源读者眼里是减分项，写清楚边界（哪些平台只能存草稿、哪些需要人工提交）反而加分。
- **诚实标注限制**。你已经知道的：页面驱动平台需要真账号、每次同步会开标签页、部分平台只能填不能发。写进 README 的 "Known limitations"，能挡掉一半「为什么发不出去」的 issue。
- **上游署名**放在 License 旁边，一句话即可：「本项目基于 [Wechatsync](https://github.com/wechatsync/Wechatsync) 二次开发，遵循 GPL-3.0。」

`CONTRIBUTING.md` 重写要点：删掉 `# hello world`、把 yarn 全部改成 pnpm（`pnpm install` / `pnpm dev` / `pnpm bundle`）、包结构改成真实的 4 个包、补「提交前必须通过 `pnpm typecheck && pnpm test`」、补 Conventional Commits 提交规范。

## 五、版本与发布规范

### 5.1 版本号怎么定

采用语义化版本，**只对扩展这一个产品发布**，所有包锁步同版本（`v2.4.2` = 所有包 2.4.2）：

| 变更类型 | 版本位 | 例子 |
|---|---|---|
| 修 bug、改文案、调选择器 | patch `x.y.Z` | 2.4.2 → 2.4.3 |
| 新增平台、新增功能、新增设置项 | minor `x.Y.0` | 2.4.3 → 2.5.0 |
| 改存储结构 / 改消息协议 / 需要用户重装 | major `X.0.0` | 2.5.0 → 3.0.0 |

### 5.2 五步发布（每次照抄）

```bash
pnpm version:bump patch        # 或 minor / major，自动改 7 个文件
# 1. 手写 CHANGELOG.md 顶部条目
pnpm typecheck && pnpm test    # 2. 门槛
pnpm bundle                    # 3. 出包
git add -A && git commit -m "chore(release): v2.4.3"
git tag -a v2.4.3 -m "v2.4.3" && git push --follow-tags   # 4. 打标
gh release create v2.4.3 ugaeo-v2.4.3.zip --title "v2.4.3" --notes-file <(sed -n '/^## v2.4.3/,/^## v2.4.2/p' CHANGELOG.md | head -n -1)   # 5. 发版
```

`pnpm version:check` 可以随时校验版本是否漂移，**建议直接放进 CI**，版本不一致就让构建失败。

### 5.3 CHANGELOG 写法

保持现在的风格即可（按版本倒序、`🐛/✨/🧪` 分类），但建议补一句格式说明：遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)，版本号遵循 SemVer。**未发布的改动先写在 `## 未发布` 段落**，发版时再改成版本号 —— 这样随时 commit 都不会忘记记录。

### 5.4 发布前检查清单（贴在 PR 模板里）

- [ ] `pnpm typecheck` 通过
- [ ] `pnpm test` 通过（含适配器一致性体检）
- [ ] `pnpm version:check` 一致
- [ ] CHANGELOG 已更新
- [ ] 新增平台已同时更新：适配器 → `BUILT_IN_ADAPTERS` → `PLATFORM_PROFILES` → README 平台表 → `docs/平台分类.md`
- [ ] `pnpm bundle` 产物能装进浏览器，版本号显示正确

## 六、后续我怎么帮你管

为了让「本地」和「GitHub」不再分叉，建议按这套约定来，我每次动手都遵守：

**分支**

- `main` 始终可发布，只接受 PR（你自己的改动可以直接 commit，但发布前必须打 tag）
- 功能分支 `feat/xxx`、修复 `fix/xxx`；一次只做一件事，方便回滚
- 发布分支不再另开（`version/x.x.x` 那套已经过时，tag 就是版本）

**提交**

Conventional Commits，中文正文可以，前缀用英文：`feat:` / `fix:` / `chore:` / `docs:` / `refactor:` / `test:`。这样一个 `git log --oneline` 就能当变更日志看。

**我每次改完必做**

1. `pnpm typecheck` + `pnpm test`（不全绿不算完成）
2. 涉及界面/协议的改动，`pnpm bundle` 并核对 zip 内容
3. 更新 CHANGELOG
4. 该升版本时用 `pnpm version:bump`，不手改
5. 告诉你「改了什么文件、验证了什么、还剩什么风险」

**我不会碰的**

你的 GitHub 账号密码 / token、Chrome 商店后台、任何真实账号的 Cookie。需要 push 时我只准备好命令，由你执行或明确授权。

## 八、下一步：需要你在本机做的 2 件事

### 1. 立刻改 GitHub 密码

密码已经出现在对话里，等同于泄露。请到 `github.com/settings/security` 改密码，并开启 2FA（这是开源维护者的基本盘：仓库一旦公开，被撞库的代价是仓库被清空）。

**我不会使用、也不会保存你提供的密码。** 原因：GitHub 早已禁止用密码做 git 操作，push 必须用 PAT 或 SSH key；而且代登录你的账号属于越权操作。

### 2. 在本机授权一次，然后执行建仓

方式 A（推荐，装了 GitHub CLI 的话）：

```bash
winget install GitHub.cli      # 只需一次
gh auth login                  # 选 HTTPS → 浏览器授权
```

方式 B（不用 CLI）：在 GitHub 网页上建一个空仓库（**不要**勾 README / .gitignore / LICENSE），然后在本机执行：

```bash
git remote add origin https://github.com/jayibidi/UGAEO.git
git push -u origin main
```

> 首次 push 会弹出浏览器登录或要求输入 PAT（Settings → Developer settings → Personal access tokens → Fine-grained，勾 `repo` 权限）。

授权完成后告诉我一声，我来跑 `git init` + 首次提交 + push，并按第三节执行 Release。
